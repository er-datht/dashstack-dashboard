## Modal Animation

shared show/hide animation for `AddEventModal` and `ConfirmModal` (fade + scale: overlay `opacity 0↔1`, card `scale(0.95) translateY(8px) ↔ scale(1) translateY(0)`; 200ms `--transition-base`/`--transition-ease-out` in, 150ms `--transition-fast`/`--transition-ease-in` out). New capability spec `modal-animation`; shared hook `src/hooks/useModalTransition.ts` holding a `"closed" | "open" | "exiting"` phase, returning `{ isRendered, isExiting, handleAnimationEnd }`; **the exit is the whole difficulty** — both components previously early-returned `null` the instant `isOpen` flipped, so the node must survive the exit. Phase is adjusted **during render** (React's "adjusting state when a prop changes"), never in an effect, so the enter class lands in the node's first painted commit; initial phase derives from `isOpen`, which is what keeps a first render with `isOpen={false}` rendering nothing. `handleAnimationEnd` needs **both** guards or it self-destructs: `e.target !== e.currentTarget` (animationend bubbles from descendant spinners/shimmer) and `phase !== "exiting"` (**the enter animation fires `animationend` on the same node**, so without this every modal unmounts ~200ms after opening). Underneath sits a `setTimeout` watchdog `EXIT_WATCHDOG_MS = 400` — a deliberate **ceiling, not a mirror** of the 150ms CSS value, so it never becomes an SCSS↔TS binding; it exists solely because a missed `animationend` would leave a permanent full-screen overlay swallowing every click, and it is cleared on `animationend`, on reopen mid-exit, and on unmount. Reduced motion overrides `animation-duration: 1ms` and **must never use `animation: none`** — with no animation there is no `animationend`, so reduced-motion users would wait on the 400ms watchdog every time; keeping it CSS-only also means no `matchMedia` and no jsdom mock. `animation-fill-mode` is asymmetric on purpose: `forwards` on exit (must hold `opacity: 0` or the card flashes back for a frame before unmount), `backwards` on enter (filling forwards would pin an identity `transform` on `.modalCard` forever, and any transform makes an element a containing block for `fixed`/`absolute` descendants plus a stacking context). Enter/exit classes are **mutually exclusive** (`cn(base, isExiting ? exit : enter)`) — two `animation-name` longhands on one node compete; the hook exposes only `isExiting` to make that the obvious form. Scroll-lock and focus-trap effects are keyed on `isRendered`, **never on the `isOpen` prop**: keying them on the prop releases `body { overflow: hidden }` at exit START, the scrollbar reappears, page width changes, and the exiting card visibly jumps sideways. Both components' release now **excludes their own node** (captured at effect setup, since React detaches refs on unmount) from `querySelectorAll('[aria-modal="true"]')` rather than reusing the old bare `querySelector` predicate — order-independent, so a stacked ConfirmModal still mid-exit keeps the lock. `AddEventModal` renders its edit-specific bits (heading, Delete button, delete target id) from an `editContext` snapshot updated only while `isOpen` is true, because `handleCloseModal`/`handleSaveEvent`/`handleDeleteEvent` in `Calendar/index.tsx` all clear `editingEvent` in the **same update** as `isModalOpen` — without the snapshot the heading flips "Edit Event" → "Add New Event" and Delete pops out of the footer mid-fade. An exiting modal is inert (keydown + overlay-click early-return; overlay deliberately **keeps** `pointer-events` so swallowed clicks can't fall through to the page underneath); `ConfirmModal` restores focus at exit START, not on unmount. Accepted: the nested delete-confirm's exit can be truncated by its parent's removal (equal durations make it a frame or two), and Escape within the 150ms window after dismissing the nested confirm also closes the parent. Side effect of `ConfirmModal` being shared: the ProductStock row-delete and Calendar page-level confirms are animated too. **`src/test/setup.ts` polyfills `window.AnimationEvent`** — jsdom 29 lacks it, so React registers the vendor-prefixed `webkitAnimationEnd` and `fireEvent.animationEnd` never reaches `onAnimationEnd`; deleting it or moving it below a react-dom import silently breaks every animation test while the browser stays fine. Browser-only verification (real timing, reduced motion, theme parity, transform-under-layout, page-width stability) lives in `e2e/modal-animation.spec.ts` via `@playwright/test` — **`channel: "chrome"` drives the system Chrome and `playwright install` must never be run** (security review: bundled Chromium lags ~130 patch revisions and is a ~350 MB CDN archive with no published integrity check); `e2e/**` is excluded from vitest (`configDefaults.exclude` is the test-defaults object itself in vitest 3.2.4 — no `.test` key) or `yarn test` tries to run Playwright specs; run with `yarn test:e2e`, and note the page-width assertion is near-vacuous on macOS overlay scrollbars so the load-bearing check samples `document.body.style.overflow` per frame instead.

## Loading Indicators

single semantic token `--color-loading-accent` in `src/index.css` (light `primary-600` → `#2b5ff7`, dark `primary-400` → `#6691ff`, forest `primary-light` → `#4ade80`) driving every page-, panel- and overlay-level loading indicator: the Suspense `LoadingFallback` in `AppRoutes.tsx`, `LoadingWrapper`, the `TableCommon` overlay, the RevenueChart/SalesDetailsChart states (inherited via `.icon-brand`, which was rewritten to consume the token and lost its per-theme nested overrides), and the ring spinners in Products / ProductDetail / Favorites (now the shared `loading-ring` mixin in `_mixins.scss`). New capability spec `loading-indicator-color`. **Four of the traps here were each silently invisible in source and only appeared in the built CSS or the browser.** (1) `color()` returns `null` for a key `$colors` does not have and **Sass then drops the entire declaration** — `color(primary-light)` compiled away, so forest on Products/ProductDetail rendered a navy `#1d3590` track with a blue `#2b5ff7` arc, never the green everyone assumed; `$colors` has numbered keys only, with `primary`/`primary-dark`/`primary-light` existing solely as CSS custom properties. (2) `[data-theme="dark"] .spinner` / `[data-theme="forest"] .spinner` override blocks outrank the base `.spinner` rule, so recolouring the base alone leaves dark and forest frozen — six such blocks existed across the three modules and the initial audit had found only one; **grep every module for `[data-theme]` blocks touching the selector you are changing**. (3) `border-primary-600` and `bg-surface-dark` **generate no Tailwind utility at all** — the numbered palette is declared in `:root`, not in `@theme`, so those classes are inert and the elements fell through to inherited colours; the whole bug survived a year because the class names read correctly. (4) Tailwind's `dark:` variant compiles to `prefers-color-scheme`, so it tracks the **OS**, not the app's `data-theme` — any `dark:` colour on a themed element is a bug, and forest is unreachable through a two-state variant. Translucent values (`--color-loading-track`, `--color-scrim`) are authored as **literal `rgba()` per theme, deliberately not `color-mix(… var(--token) …)`**: Lightning CSS cannot statically resolve a mix over a custom property and emits an `@supports`-guarded fallback of the bare **opaque** colour, which would make the track equal the arc (a uniform ring with no visible rotation) and turn the scrim fully opaque; the e2e spec compares resolved channels to catch drift between a token and its `rgba` twin. The scrim derives from `--color-background`, **not `--color-surface`** — in dark and forest the surface is *lighter* than the background, so a surface-based scrim lightens the content it is supposed to dim. Loading **text** stays `--color-text-secondary`: primary-coloured text beside a primary spinner reads as a link. Dark clears the 3:1 WCAG non-text contrast floor by only 0.49 (`#6691ff` on `#344152` = 3.49:1), so it is the theme that breaks first if `--color-surface` is darkened. Verification is browser-only — **Vitest swaps CSS Modules for a non-scoped proxy and cannot resolve a computed style**, so `e2e/loading-accent-color.spec.ts` drives `/table` and asserts computed colours per theme (shared setup in `e2e/helpers.ts`, extracted from `modal-animation.spec.ts`); `e2e/**` stays excluded from vitest and `playwright install` must never be run. Out of scope by decision: the six button-internal spinners (they keep `text-on-primary` — an accent spinner on an accent button is invisible), the dead DealDetailsTable loading CSS, the unused `loading-shimmer` mixin, `EditProduct`'s indicator-less branch, and extracting a shared `Spinner` component.
